# Security posture

**Status:** authoritative. Records what is enforced, what is deliberately
accepted, and why — so that accepted risks are not re-litigated as findings on
every sweep.

Last reviewed: 2026-08-18 (issue #424).

---

## What this site is

A static personal blog built with Astro and served from GitHub Pages. No
authentication, no cookies, no forms, no user-generated content, no
state-changing endpoints. Posts are written by the author and by automated
pipelines in this repo (the link-monitor auto-repair workflow opens PRs against
`src/posts/**`).

That last point matters more than "single author" suggests, and it is the reason
the sanitizer below is worth having.

---

## Enforced

### HTML sanitization — the first line of defence

`astro.config.mjs` runs `rehype-sanitize` over the markdown pipeline with a
custom schema (`sanitizeSchema`). The schema extends the library default rather
than replacing it, adding:

- `figure`, `figcaption`, `aside` and the SVG tag set to `tagNames`
- a shared `contentAttributes` list (`className`, `data*`, and the ARIA
  attributes) applied to every element that needs it

**Do not swap this for the default schema.** The default does not permit `role`,
and roughly 90 posts carry `role="group"` on `.flow` / `.arch` diagram blocks
from the accessibility work in #414. Replacing the schema would strip that
silently — the build would pass and the a11y regression would ship.

Verified in built output, not just in config: a `.flow`-heavy post's `dist/`
HTML retains 17 `role="group"` attributes and its `.flow`/`.arch` classes.

The RSS path (`src/pages/feed.xml.ts`) sanitizes separately with
`sanitize-html`. Both paths sanitize; they are not inconsistent.

### CSP, as far as a `<meta>` tag can go

Delivered via `<meta http-equiv>` in `BaseLayout.astro`. GitHub Pages cannot send
real HTTP response headers, so this is the only available mechanism.

## Accepted, with reasons

### `script-src 'unsafe-inline'` stays

**Decision (2026-08-18): accept. Rely on the sanitizer.**

Astro 7 can compute sha256 hashes for inline scripts at build time
(`security.csp`). Tested on a scratch branch, and it does not work here:

```
inline scripts on a representative page: 8
hashes generated by Astro:               8   <- coincidence, not a match
scripts whose hash actually appears:     2
```

Across a 25-page sample, **133 of 183 inline scripts would have been blocked.**

The cause is structural, not a configuration mistake. All four authored inline
scripts use `is:inline`, which is a direct instruction to Astro not to process
them — so Astro never sees them to hash them. JSON-LD blocks go through
`set:html` and are missed the same way.

And `is:inline` is load-bearing. The theme-flash snippet in `BaseLayout.astro`
must execute before first paint; an Astro-processed script is bundled and
deferred, which reintroduces the flash it exists to prevent. So "stop using
`is:inline`" trades a CSP directive for a visible rendering defect.

The remaining option — post-processing `dist/` to compute and inject hashes for
every inline script — is perhaps thirty lines plus a build step. It was declined
because its failure mode is silent: `report-uri` and `report-to` are **also**
ignored in meta-delivered CSP, so a wrong hash produces no telemetry. The
symptom would be readers getting a theme flash and a dead theme picker, with CI
green.

**What this costs:** an attacker who could inject HTML into a post could execute
script. What prevents that is the sanitizer above, not the CSP. Revisit if the
site ever renders content this repo does not control.

**Worth recording:** a count-based check (8 hashes, 8 scripts) passed this. Only
hashing each script body and testing membership in the policy caught it. If
someone revisits this, verify by hashing, not by counting.

### No clickjacking protection

**Decision (2026-08-18): accept.**

`frame-ancestors` is ignored when CSP is delivered via `<meta>` (CSP Level 3),
and `X-Frame-Options` has no meta equivalent. The site is therefore embeddable
in an iframe anywhere.

Clickjacking requires an action worth hijacking. This site has no authenticated
actions, no forms, and no state-changing endpoints — framing it yields the
attacker a framed blog. The only real fix is fronting GitHub Pages with an edge
that can send response headers, which means taking on a permanent operational
dependency and a DNS/TLS migration to deliver one header protecting nothing.

A JavaScript frame-buster was also declined: bypassable, and it would add inline
script complexity in the same breath as the section above.

**Revisit if:** the site gains authentication, forms, or any embedded
interactive tool with side effects.

## Not accepted — fixed

- **Gist `<script>` embeds** (issue #424 item 2). Seven posts once carried live
  `<script src="https://gist.github.com/….js">` tags that the CSP blocked, so
  they rendered as nothing. All references are now plain markdown links; no
  script embeds remain.
